**Weipeng Shi, Wenhu Qin, Zhonghua Yun, Chao Wu, Yukun Yang, and Tao Zhao**

这篇笔记介绍 NJLCC2022——**NanJing Land Cover Classification in 2022**，一个由我们自己用无人机在南京采集的地表覆盖数据集。它对应的是下面这篇论文：

> W. Shi, W. Qin, Z. Yun, C. Wu, Y. Yang, and T. Zhao, "Semantic Representation Fusion-Based Network for Robust Land Cover Classification in Foggy Conditions," *IEEE Transactions on Geoscience and Remote Sensing*, 2023, 61: 1–16.

## 为什么要自己采一个雾天的数据集

动机可以用一句话概括：**现有地表覆盖数据集几乎都是晴天采集的，而实际应用中雾天会显著拉低模型精度。**

这不是一个可以靠数据增强糊弄过去的问题。Potsdam、ISPRS 这些经典数据集在理想天气下采集，模型在上面能刷出很好的 mIoU，可真到雾天航拍上，分类质量会明显下降、泛化很差。根源在于数据分布本身缺了那一段——模型从来没在那种成像条件下被训练过。

所以这个数据集有三个直接目标：

- 量化「晴天 → 雾天」的精度衰减幅度；
- 研究雾天与晴天影像在视觉表征上的共性与差异，作为设计鲁棒模型的依据；
- 提供真实的双域（晴/雾）数据，用于迁移学习。

## 采集参数

| 项目 | 参数 |
| --- | --- |
| 平台 | DJI Mavic 3 无人机 |
| 波段 | RGB 三个波段（红、绿、蓝） |
| 飞行高度 | 200 m |
| 地面采样距离 (GSD) | 4 cm/pixel |
| 影像数量 | 22 张正射纠正影像（截至 2023-04-01） |
| 其中雾天 / 晴天 | 9 张 / 13 张 |
| 平均分辨率 | 9000 × 9000 像素 |
| 类别数 | 5 类 |

几个数字值得停下来看一下。**200 m 的飞行高度配 4 cm/pixel 的 GSD**，意味着地面特征尺度相当精细——4 cm 一个像素，一辆车大约是几十个像素的量级，这对小目标是好事。**平均 9000×9000** 意味着单张影像就有约 8100 万像素，这比常见的遥感基准大了一到两个数量级，也直接决定了它必须切块之后才能训练。

## 采样设计：刻意跨越城乡

22 张影像分散采自江苏省南京市两个区域：城区**玄武区**（经度约 118.78–118.87，纬度约 32.05–32.07）和郊区**江宁区**（经度约 118.86–118.87，纬度约 31.91–31.93）。这样设计是为了**降低模型偏置**——如果只在城区采样，模型学到的很可能只是城市地物形态的先验，一到郊区就失效。

下面是采集清单的一部分（完整 22 行见数据集说明）：

| 样本 ID | 采集日期 | 雾天类型 | 经度 | 纬度 |
| --- | --- | --- | --- | --- |
| ortho1 | 2023-02-06 | 浓雾 | 118.818251 | 32.064312 |
| ortho2 | 2023-02-06 | 浓雾 | 118.823017 | 32.065051 |
| ortho3 | 2023-02-06 | 浓雾 | 118.816626 | 32.066614 |
| ortho4 | 2022-11-03 | 晴 | 118.809120 | 32.054298 |

| ortho7 | 2022-12-07 | 中雾 | 118.861529 | 31.914914 |

| ortho10 | 2022-12-07 | 中雾 | 118.874873 | 31.914486 |

这张表里有个容易被忽略但很重要的信息：**雾天影像高度集中在 2022-12-07 / 12-09 / 2023-02-06 三个采集日**，而晴天影像跨了 2022-10 到 2022-12 的多个批次。这意味着天气条件与采集时间存在**相关性**——如果你用随机划分训练/测试集，模型有可能「记住」某个时间段的成像特征，从而高估泛化能力。**划分时应该按采集日期分组，而不是随机划分。**

另外注意雾天还分了三档：浓雾（Thick）、中雾（Moderate）、轻雾（Thin）。这个分级让「雾的浓度」成为一个可控变量，而不只是二元的「有雾/无雾」。

## 标注方案：5 类固定 RGB 颜色

标注是**调色板式 RGB**，每个类别一个固定颜色：

| 类别 | RGB | 说明 |
| --- | --- | --- |
| Clutter Background（杂物背景） | (0, 0, 0) | 黑色，非目标区域 |
| Car（车辆） | (0, 128, 0) | 深绿色 |
| Playground（操场） | (128, 0, 128) | 紫色 |
| Water（水体） | (0, 0, 128) | 深蓝色 |
| Building（建筑） | (128, 0, 0) | 深红色 |

这个标注方式在遥感分割里很常见，好处是**目视检查极其直观**——打开标签图一眼就能看出有没有错标，因为颜色和人眼对地物的认知直接对应（建筑红、水体蓝，跟大多数底图的配色习惯一致）。

但它有一个必须注意的坑：**这些标签图不能直接当训练输入**。如果你沿用上一篇文章提到的做法——把 RGB 标签按调色板反查成 ID 编码——一定要确认反查表是完整的、且没有被截断。在一段超长的代码里（比如我处理 Potsdam 时写的那种），调色板只定义了前几个类别，后面全是 `...`，而标签图里恰好出现了没被列出的颜色，那么那些像素会静默地变成背景类。不报错，指标只是莫名其妙地低。

5 类里最值得注意的是 **Clutter Background** 单独占一类。这不是「无标签」，而是显式标注的背景——道路、裸土、植被等不感兴趣的地物都被归到这一类。用 `ignore` 标签还是用显式背景类，是有实质区别的：显式背景类能防止模型把道路误判成建筑，代价是需要更多标注人力。

## 我自己的使用笔记

这个数据集我主要拿来做两件事。

第一件是**鲁棒性评测的基准**。绝大多数论文报告「模型在雾天掉多少个点」，用的都是自己在某个合成雾（加雾函数）上生成的数据。合成雾的问题是它太规则了——物理模型和真实大气散射完全是两回事。真实雾影像的价值就在于它包含了采集时长的不均匀、边缘的散射衰减、整体对比度下降这些合成过程很难复现的细节。

第二件是**双域评测协议的来源**。这里有个我在做实验时才意识到的问题：由于雾天和晴天在采集时间上高度相关，「随机划分」会给出虚高的结果。正确的协议应该是：

1. 按**采集日期**分组划分训练/测试，而不是按图像随机划分；
2. 报告晴天→晴天、晴天→雾天两组指标，而不是只报一个总 mIoU；
3. 5 类里 `Car` 和 `Playground` 像素占比通常很低，要单独看它们的召回——总分被 `Building` 和背景类撑起来很容易。

第 1 点是我踩过的坑，写在这里以免下次再犯。
